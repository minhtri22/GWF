# GWF v0.8.7 — Agent Interoperability Foundation

## 1. Status

**Document status:** architecture specification / implementation not authorized.

**Baseline:** GWF v0.8.5 `main` at `f7bbe2e91a148e11397406327ebf3d3389f7c6a7`.

This document defines the future interoperability boundary between GWF and external agent runtimes. It does not add MCP, ARC, A2A, Codex, Claude, Gemini, IDE, model-provider, or agent-pool code.

## 2. Core design decision

GWF must distinguish two different execution problems.

### 2.1 Harness agents

Examples include Codex, Claude, Gemini, or IDE-integrated agent environments where the **harness itself** provides material execution value such as:

- repository understanding;
- tool loops;
- shell/sandbox execution;
- editing workflows;
- IDE state;
- session/thread semantics;
- built-in review or coding workflows.

GWF should exploit the harness rather than reduce it to a bare model endpoint.

### 2.2 Agent Pool workers

A separate class consists of role-specific Agent Pool workers. They may use free, local, low-cost, community, or otherwise specialized models.

Agent Pool is a **resource/orchestration class**, not a transport protocol. ARC is one planned communication transport through which such workers may be discovered or invoked; ARC itself does not provide free models and does not imply any particular cost class.

They are **not fallbacks by definition**.

They may be the intended primary executor of a node from the beginning, for example:

- paper scout;
- GitHub/source-code scout;
- documentation researcher;
- junior developer for a small/simple implementation;
- test writer;
- log triage worker;
- metadata extractor;
- low-risk batch worker.

Fallback is only one possible routing policy. Agent Pool workers are first-class execution resources with their own roles, capabilities, authority limits, and evidence contracts.

## 3. Architectural principle

GWF remains the governance authority regardless of executor type.

```text
                       GWF
                        │
              Governance / Authority
                        │
              Workflow / Node Graph
                        │
          ┌─────────────┴─────────────┐
          │                           │
   Harness execution             Agent Pool
          │                           │
  Codex / Claude / Gemini       ARC-connected agents
  / IDE agent harnesses         free/local/cheap/specialist
          │                           │
          └─────────────┬─────────────┘
                        │
                  normalized evidence
                        │
                     QA / gates
```

The executor may reason and act within granted scope. It does not own:

- authoritative workflow state;
- gate mutation;
- scientific threshold mutation;
- lineage rewriting;
- final release completion;
- silent executor substitution where policy forbids it.

## 4. Why this is not an n8n-style integration layer

The purpose is not to accumulate SaaS connectors.

GWF owns:

- role requirements;
- execution authorization;
- frozen inputs;
- authority scope;
- evidence expectations;
- retry/recovery semantics;
- provenance;
- QA/gates;
- handoff;
- authoritative completion.

External agent systems provide execution capacity and harness-specific capabilities.

## 5. Future abstraction model

The core should eventually understand **roles, capabilities, bindings, and execution envelopes**, not vendor-specific details.

### 5.1 `AgentRole`

A semantic job identity, for example:

- `paper_scout`
- `source_code_scout`
- `junior_dev`
- `senior_dev`
- `qa_reviewer`
- `statistical_reviewer`
- `adversarial_reviewer`

A role expresses what work is expected, not which model/vendor must execute it.

### 5.2 `AgentCapability`

Capabilities may include, for example:

- repository_read
- repository_write
- shell_execution
- web_research
- paper_search
- code_search
- long_context_review
- structured_output
- test_execution
- image_understanding

Capabilities must be descriptive. They are not quality scores.

Execution constraints such as locality, privacy, network access, data residency, maximum authority, or cost ceiling are policy constraints rather than capabilities. For example, `LOCAL_ONLY` belongs in an execution/locality constraint, not in the capability list.

### 5.3 `AgentBinding`

A binding resolves a role/node to an executor identity under policy. Executor resource class, provider, and transport are separate dimensions: for example, an `AGENT_POOL` executor may be reached through `ARC`, while a `HARNESS` executor may use a native driver.

Conceptual fields:

- `binding_id`
- `binding_revision`
- `node_or_workunit_ref`
- `role`
- `executor_class`
- `agent_id`
- `provider_ref`
- `transport_ref`
- `model_identity`
- `harness_identity`
- `agent_revision`
- `capabilities`
- `authority_scope`
- `risk_class`
- `cost_profile`
- `privacy_profile`
- `binding_mode`: `DYNAMIC | FROZEN`
- `selection_policy_ref`
- `equivalence_policy_ref`
- `resolved_at`
- `valid_from`
- `valid_until`

`DYNAMIC` means the policy may resolve a different compatible executor for a **future attempt**. Once an attempt is dispatched, its resolved binding is immutable for that attempt and must be recorded in the execution envelope. `FROZEN` means the identity dimensions declared material by policy are fixed across attempts unless an explicitly governed amendment authorizes otherwise.

### 5.4 `AgentExecutionEnvelope`

All execution paths should normalize enough metadata for GWF to reconstruct what happened.

Minimum conceptual fields:

- `execution_id`
- `orchestration_id`
- `node_or_workunit_id`
- `attempt`
- `role`
- `binding_id`
- `executor_class`
- `agent_identity`
- `model_identity`
- `harness_identity`
- `protocol_or_transport`
- `external_session_id`
- `external_trace_id`
- `frozen_input_hash`
- `skill_revision`
- `authority_scope`
- `started_at`
- `finished_at`
- `status`
- `outputs`
- `evidence_refs`
- `tool_event_refs`
- `result_hash`
- `handoff_ref`

The envelope is evidence about execution. It is not itself a PASS/FAIL scientific verdict.

A future implementation should define an executor-status vocabulary distinct from GWF gate outcomes. At minimum it should distinguish states equivalent to `PREPARED`, `DISPATCHED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELLED`, `TIMED_OUT`, and `ABANDONED`. `SUCCEEDED` means the executor returned the contractually expected result envelope; it does **not** mean GWF QA/gates passed or the node is authoritatively complete.

## 6. Harness execution family

Harness integration exists to preserve and exploit the native agent environment.

Examples of future adapters may include:

- Codex harness / app-server-style integration;
- Claude coding/agent harness;
- Gemini CLI/agent harness;
- IDE-hosted agents.

A harness adapter should translate between GWF's governed node contract and the native session/task model without hiding:

- which harness executed the work;
- which session/thread performed it;
- which repository/workspace was visible;
- which tools were available;
- what result/evidence returned.

A harness adapter must not directly declare a GWF node complete without GWF verification.

## 7. Agent Pool resource family and ARC transport

Agent Pool is the resource class. ARC is treated as one future **Worker Fabric transport** for reaching members of that pool, not as a fallback-only mechanism and not as the source of the models themselves.

A pool may contain agents backed by:

- local models;
- free/community endpoints;
- low-cost hosted models;
- specialized research/coding models;
- small models intended for narrow roles.

Conceptually:

```text
Agent Pool
  ├── paper-scout-01
  ├── github-scout-01
  ├── junior-dev-qwen
  ├── test-writer-small
  └── log-triage-local
```

GWF may assign one of these agents as the primary executor of a node when the role/capability/risk contract permits it.

## 8. Node-level assignment model — future parking lot

The intended future relationship is:

```text
NODE
  ↓
ROLE
  ↓
REQUIRED CAPABILITIES
  ↓
AUTHORITY + RISK + PRIVACY CONSTRAINTS
  ↓
AGENT BINDING
  ↓
EXECUTION
  ↓
EVIDENCE
  ↓
QA / GATE
```

Example:

```text
reference.paper_search
    role = paper_scout
    executor = ARC agent

reference.code_search
    role = source_code_scout
    executor = ARC agent

software.small_utility
    role = junior_dev
    executor = ARC agent

software.architecture_review
    role = senior_dev
    executor = Codex harness

software.independent_qa
    role = qa_reviewer
    executor = Claude harness
```

This is a design target only. Node-level agent binding is not part of v0.8.5 and is not authorized for implementation by this document.

## 9. Routing policy dimensions

Future routing may consider:

- required capability;
- node complexity;
- authority level;
- risk class;
- scientific sensitivity;
- privacy/locality requirement;
- availability;
- latency;
- cost profile;
- reproducibility requirement;
- harness/tool requirement.

No single scalar "best agent" score is required or assumed.

## 10. Dynamic versus frozen binding

### 10.1 Dynamic binding

Appropriate for low-risk/non-normative work when executor identity is not scientifically or operationally material.

Examples may include metadata extraction, reference scouting, formatting, or simple isolated coding tasks.

Dynamic binding does not mean mid-attempt executor mutation. Resolution occurs before dispatch of each attempt; reassignment after a failure creates a new attributable attempt with an explicit reassignment reason.

### 10.2 Frozen binding

Required when executor identity could affect comparability, reproducibility, authority, or study validity.

Examples may include:

- confirmatory scientific adjudication;
- high-impact normative review;
- a controlled benchmark comparing agent behavior;
- reproducibility-sensitive execution;
- release authority steps.

A frozen binding must not be silently substituted.

The policy that freezes a binding must state which identity dimensions are material, such as agent identity, model/version, harness/revision, tool set, or execution environment. If the protocol permits an executor equivalence class, that class must be defined prospectively, identify which dimensions may vary, and may not be inferred after outcomes are observed.

## 11. Delegation hierarchy

Future workflows may intentionally use a senior/junior structure.

```text
Lead / specialist harness agent
       │
       ├── Agent Pool junior worker A
       ├── Agent Pool junior worker B
       ├── Agent Pool test worker
       └── Agent Pool research scout
```

However, delegation must remain observable to GWF.

An external senior agent must not create an untracked hidden multi-agent hierarchy whose outputs enter authoritative GWF state without provenance.

If agent-created delegation is supported later, each delegated execution must still produce an attributable execution envelope or an equivalent governed child record. A delegated child may receive only authority equal to or narrower than the authority delegated to its parent; delegation must never create privilege escalation.

## 12. Transport versus governance

Transport/protocol is not authority.

Future transports may include:

- native harness drivers;
- MCP-facing surfaces;
- ARC;
- A2A;
- local direct execution;
- future protocols.

GWF core should avoid baking transport-specific semantics into scientific/software governance.

A future implementation should prefer an interface conceptually similar to:

```text
AgentTransport
  discover()
  capabilities()
  dispatch()
  status()
  stream_events()
  cancel()
  collect_result()
```

The transport returns execution evidence. GWF still applies policy and gates.

## 13. MCP boundary

MCP is a different problem from Agent Pool execution.

Its primary future use is to expose governed GWF context/actions to external clients or agent harnesses, for example:

```text
ChatGPT / IDE / agent client
          ↓
         MCP
          ↓
         GWF
```

Potential MCP-facing operations should be governance-oriented, such as:

- read project state;
- read current workunit;
- read governed artifacts/evidence;
- propose artifact revision;
- submit execution result;
- report problem;
- propose recovery;
- request an authorized change set.

MCP must not provide unrestricted primitives such as arbitrary database mutation, `force_pass`, silent gate mutation, lineage deletion, or force merge.

Any MCP operation capable of changing GWF state must map to a governed GWF command with the same authority check, idempotency semantics, audit record, and verification requirements as a native call. MCP transport never becomes an alternate authority path.

## 14. Cross-system trace identity

The future interoperability layer should preserve one reconstructable execution chain.

Conceptually:

```text
orchestration_id
    ↓
node/workunit execution
    ↓
agent execution_id
    ├── Codex session/thread
    ├── Claude session
    ├── Gemini session
    ├── ARC trace/task
    ├── MCP request trace
    └── GitHub change set
```

External trace IDs must be recorded as foreign identities, not substituted for GWF's own authoritative execution ID.

## 15. Failure and substitution semantics

Executor failure and executor substitution are distinct events.

A future policy must distinguish at least:

- retry same agent / same frozen input;
- resume same harness session;
- assign another compatible agent under dynamic binding;
- request human approval before substitution;
- stop because binding is frozen.

Substitution must never be silent.

When a new agent performs an attempt, lineage must preserve the prior attempt and the reason for reassignment.

## 16. Research-specific constraint

In research workflows, executor substitution may itself be scientifically material.

If agent/model identity can affect the measured outcome or adjudication, the binding must be frozen or the protocol must explicitly pre-authorize an equivalence class.

A free/local Agent Pool worker is therefore fully valid as a primary executor when assigned prospectively, but it must not be swapped into a confirmatory role after results are seen unless the study's governance explicitly permits it.

## 17. Security boundary

External agents receive only the authority and secrets required for their node.

The interoperability layer must preserve the existing principle that provider credentials remain in host-side/server-side credential resolution rather than public/static UI surfaces or persisted artifact payloads.

Future agent execution should prefer opaque connection references over raw reusable secrets. Secret material must not be serialized into `AgentBinding`, `AgentExecutionEnvelope`, tool-event logs, evidence payloads, or static UI artifacts. Secret resolution occurs only at the authorized execution boundary, with redaction of provider-returned credential material before persistence.

## 18. Acceptance criteria for future implementation

Before v0.8.7 can be called implemented, the system should demonstrate at least:

1. harness and Agent Pool executors are represented as distinct resource classes;
2. executor/resource class is represented separately from transport/protocol;
3. Agent Pool workers can be primary node executors, not only fallback targets;
4. role and capability requirements are separable from concrete agent identity;
5. execution constraints such as locality/privacy are separable from capabilities;
6. all executor paths produce a normalized execution envelope with executor status distinct from GWF gate status;
7. external session/trace IDs are correlated with GWF lineage;
8. dynamic binding resolves before each attempt and the resolved binding is immutable within that attempt;
9. frozen bindings define the identity dimensions that are frozen, and any equivalence policy is prospective;
10. agent substitution is always observable and creates attributable lineage;
11. delegated children cannot exceed parent authority;
12. GWF, not the external transport, owns authoritative completion;
13. authority/risk/privacy constraints can block an otherwise capable agent;
14. mutation-capable MCP operations traverse normal GWF authority/idempotency/audit/verification paths;
15. no integration persists provider secrets in execution envelopes, evidence, logs, GitHub Pages, or static UI;
16. a harness integration retains harness-specific value instead of reducing the harness to a bare completion API;
17. node-level role assignment can be added later without breaking the core execution model.

## 19. Future prioritization — planning only

The current planning preference is:

1. preserve an agent-neutral execution envelope and trace identity first;
2. make ChatGPT the preferred interactive/operator-facing client path where practical, using a governed MCP-facing boundary rather than exposing raw secrets or unrestricted mutation;
3. make Codex the first high-value harness execution target because the harness itself provides repository/tool/session value;
4. support Claude and Gemini as additional harness families without changing GWF governance semantics;
5. support ARC as a first-class Agent Pool / Worker Fabric for role-specific free/local/cheap/specialized workers;
6. add node-level role→capability→agent binding only after a real project creates the need.

This is a sequencing preference, not an implementation authorization and not a quality ranking of model vendors. ARC workers may be primary executors from the start for suitable nodes.

## 20. Implementation authorization boundary

Passing this document's QA does not authorize code changes. Any MCP server, harness adapter, ARC transport, agent registry, node binding, or routing implementation requires a separate explicit implementation authorization.
