# GWF v0.8.4 — GitHub Plugin & SHA-Safe QA

## Baseline

v0.8.4 starts from verified v0.8.3 main commit:

`11117299b41676f899cc54d108957f5ee596b185`

At that SHA, the v0.5.1, v0.6, v0.7, v0.8, v0.8.1, v0.8.2 and v0.8.3 workflows all passed.

## Scope

v0.8.4 adds a host-plugin boundary for GitHub operations and makes SHA comparison a standard QA requirement for source/document writes.

### Plugin connection registry

A project can register a plugin connection with:

- plugin type;
- opaque external connection reference;
- explicit capabilities;
- non-secret metadata;
- active/disabled lifecycle.

Credentials are intentionally not stored in GWF. Common secret fields and GitHub token prefixes are rejected by the persistence boundary.

### GitHub repository binding

A GitHub connection can be bound to a repository with:

- repository full name;
- default branch;
- write policy;
- branch allowlist.

Default policy is `FEATURE_BRANCH_ONLY`. Direct default-branch changes require explicit `DIRECT` policy and a HUMAN actor.

### Reference GitHub REST adapter

v0.8.4 includes a concrete `GitHubRestAdapter` using GitHub's Git Data API. A host attaches it with an external credential resolver:

- GWF passes only the opaque connection reference to the resolver;
- the resolver returns a credential in process memory;
- the adapter asks for the credential at request time and does not persist it;
- multi-file writes create blobs → tree → commit and update the branch ref with `force=false`;
- non-fast-forward ref updates are surfaced as stale-SHA failures.

The adapter attachment itself is intentionally not exposed as a public credential-bearing API endpoint.

### SHA-safe change sets

A change set freezes:

- expected branch HEAD SHA;
- target branch;
- file operation;
- expected blob SHA for UPDATE/DELETE;
- proposed content SHA-256;
- commit message;
- manifest hash.

Execution is:

`PREPARED → PREFLIGHT_PASS → COMMITTED → VERIFIED`

Stale remote state becomes `STALE`. Failed post-write verification becomes `VERIFICATION_FAILED`.

### Standard QA

The normative procedure is in `docs/GITHUB_SHA_QA_STANDARD.md`.

A GitHub commit is not QA-complete merely because the provider reports success. GWF must re-fetch and verify:

- commit parent SHA;
- resulting branch HEAD SHA;
- every affected file's content SHA-256 or deletion.

## Recovery mode clarification

Recovery remains configurable:

- `AUTO` permits agent retry when risk/normative/retry-budget policy allows;
- `HUMAN_APPROVE` pauses before retry for authenticated human approval.

GitHub stale-SHA conflicts are different: AUTO mode does not authorize silently changing an expected SHA. A new frozen change set is required.

## Non-goals

- GWF does not store GitHub credentials.
- No GitHub administration/secrets access is required by this design.
- This increment does not claim GitHub server-side branch protection replaces GWF checks; both may be used.
- This increment implements the commit adapter contract and SHA verification path. Additional provider operations can be added through the same plugin boundary without weakening this QA contract.
