# GWF v0.8.6 — Research Reference Acquisition Specification

## 1. Status

**Document status:** specification-only / implementation not authorized.

**Baseline:** GWF v0.8.5 `main` at `f7bbe2e91a148e11397406327ebf3d3389f7c6a7`.

This document defines a future extension to the research domain. It does **not** modify the current 17-phase research workflow, runtime, plugin system, database schema, or pilot behavior. Document QA PASS is necessary but **not sufficient** to begin implementation; coding remains prohibited until a separate explicit implementation authorization is given.

## 2. Problem statement

The current research package already contains `phase_01_prior_art_and_novelty`, a `prior_art_landscape` artifact, and a `literature_reviewer_v2` skill with `source_retrieval` as a tool requirement.

That is directionally correct but incomplete for reproducible research. The current contract does not make reference acquisition a first-class governed evidence chain. In particular, it does not require the system to preserve:

- where it searched;
- which exact queries were used;
- which candidate references were seen and rejected;
- which papers, repositories, standards, specifications, or technical documents were retained;
- the immutable identity of a paper or source-code snapshot;
- the relationship between a paper and its implementation, when known;
- the exact Git commit read from a repository;
- which current research claim is supported, contradicted, borrowed from, or differentiated from each reference;
- when the reference was acquired relative to study lock and fresh-outcome inspection.

Without these controls, a future agent may produce a plausible prior-art summary while losing enough provenance that novelty, reproducibility, and retrospective audit become weaker than the rest of GWF's research governance.

## 3. Objective

Introduce a governed **Reference Acquisition layer** before novelty/hypothesis commitment so that research references become traceable evidence rather than unstructured notes.

The target lifecycle is conceptually:

```text
research goal
    ↓
reference acquisition
    ↓
prior-art synthesis + novelty assessment
    ↓
hypothesis
    ↓
formalization
    ↓
protocol + study lock
    ↓
...
```

The exact phase numbering is deliberately **not frozen by this document**. A future implementation may insert a dedicated phase or split the existing prior-art phase, but it must preserve the semantics defined here.

## 4. Scope

Reference Acquisition covers four reference classes.

### 4.1 Scientific papers

Examples include peer-reviewed papers, preprints, conference papers, technical reports, theses, and other citable scientific works.

Required identity should prefer stable identifiers where available, such as DOI, arXiv identifier/version, publisher identifier, or another canonical publication identifier.

### 4.2 Source-code implementations

Examples include:

- official repositories linked by a paper;
- author-maintained reference implementations;
- independent reproductions;
- benchmark implementations;
- repositories implementing a relevant mechanism even when no paper is linked.

For Git repositories, a mutable branch name is insufficient. The retained reference must resolve to an exact commit SHA for the material actually inspected.

### 4.3 Standards, specifications, and official technical documentation

These may be primary references when the research question depends on a protocol, system contract, API, hardware behavior, language/runtime rule, or formal specification.

### 4.4 Supporting engineering evidence

Issues, pull requests, discussions, release notes, and similar sources may be retained when they materially clarify an implementation or failure mode. They are supporting evidence, not automatically equivalent to a scientific paper or normative specification.

## 5. Non-goals

v0.8.6 Reference Acquisition is **not** intended to:

- become a general-purpose web search engine;
- replace a literature reviewer with ranking heuristics;
- claim novelty merely because no retrieved reference matches a query;
- treat GitHub popularity as scientific evidence;
- automatically import or execute third-party code;
- silently modify a frozen hypothesis after observing fresh study outcomes;
- use post-outcome retrieval as retroactive preregistration;
- make a source authoritative only because an agent cited it.

## 6. Proposed governed artifacts

### 6.1 `reference_query_plan`

A prospective artifact describing the intended search before retrieval begins.

Minimum fields:

- `research_question_ref`
- `search_objectives`
- `source_classes`
- `providers_or_indexes`
- `query_families`
- `inclusion_criteria`
- `exclusion_criteria`
- `time_boundary`
- `language_boundary`
- `repository_search_policy`
- `stop_rule`
- `known_blind_spots`

The purpose is not to freeze exact natural-language wording forever, but to make the search strategy auditable and prevent an agent from retrospectively searching only for evidence that supports a preferred narrative.

### 6.2 `reference_registry`

The canonical set of candidate and retained references seen during acquisition.

Each record should contain, where applicable:

- `reference_id`
- `reference_type`: `PAPER | REPOSITORY | SPECIFICATION | DOCUMENTATION | ENGINEERING_EVIDENCE`
- `title`
- `authors_or_owners`
- `canonical_identifier`
- `canonical_url`
- `retrieved_at`
- `retrieval_provider`
- `query_ref`
- `disposition`: `RETAINED | REJECTED | DUPLICATE | UNAVAILABLE`
- `disposition_reason`
- `relevance_tags`
- `license_or_access_notes`
- `identity_fingerprint`

For papers, `identity_fingerprint` should resolve the exact publication/preprint version used where possible.

For Git repositories, the registry additionally requires:

- `repository_full_name`
- `observed_default_branch`
- `commit_sha`
- `relevant_paths`
- `linked_publication_ids`
- `repository_license`

A repository URL without an exact inspected commit is insufficient for a reproducible retained code reference.

### 6.3 `reference_evidence_map`

A structured relationship between references and the current research reasoning.

Minimum relation types:

- `SUPPORTS`
- `CONTRADICTS`
- `IMPLEMENTS`
- `REPRODUCES`
- `INSPIRES`
- `BORROWS_METHOD_FROM`
- `DIFFERS_FROM`
- `BOUNDS_NOVELTY`

The evidence map must distinguish what the source explicitly demonstrates from what the current researcher infers.

### 6.4 `reference_acquisition_report`

A compact audit artifact summarizing:

- search coverage;
- retained reference count by class;
- rejected/duplicate/unavailable counts;
- closest prior work;
- closest implementation analogues;
- unresolved search gaps;
- acquisition limitations;
- temporal boundary relative to study lock;
- handoff into `prior_art_landscape` and `novelty_assessment`.

## 7. Paper ↔ source-code linkage

Paper and code references must remain separate records even when they are linked.

Example conceptual relation:

```text
paper:P123
   │
   ├── IMPLEMENTED_BY → repo:R77 @ commit abc123...
   └── REPRODUCED_BY  → repo:R91 @ commit def456...
```

This avoids conflating a paper's claims with the behavior of a mutable repository.

A paper may have no available code. A repository may implement an idea without being the paper's official implementation. The registry must preserve that distinction.

## 8. Temporal integrity boundary

Reference acquisition has two modes.

### 8.1 `PRE_STUDY`

Used before hypothesis/protocol lock. References may influence:

- problem framing;
- novelty assessment;
- hypothesis design;
- baseline selection;
- mechanism decomposition;
- benchmark choice.

### 8.2 `POST_OUTCOME 

Used after fresh outcomes have been inspected.

Post-outcome references may inform:

- discussion;
- interpretation;
- limitations;
- follow-up hypotheses;
- a new lineage branch.

They must **not** silently rewrite the frozen novelty claim, hypothesis, target, metric, threshold, cohort, or success gate of the already locked study.

Every retained reference therefore needs an acquisition timestamp and an acquisition mode.

## 9. Reference acquisition workflow

The intended high-level sequence is:

```text
resolve research goal
        ↓
freeze query plan
        ↓
search papers
        ↓
search repositories/source code
        ↓
search standards/official docs where relevant
        ↓
normalize identities
        ↓
deduplicate
        ↓
resolve paper↔code relations
        ↓
classify retained/rejected/unavailable
        ↓
map references to claims/mechanisms
        ↓
reference QA
        ↓
prior-art + novelty synthesis
```

Retrieval may be parallelized later, but the resulting evidence must be normalized into one authoritative registry.

## 10. Proposed gates

### `reference_plan_ready`

PASS only when the research question, intended source classes, inclusion/exclusion rules, search boundaries, and stop rule are explicit.

### `reference_identity_ready`

PASS only when retained references have reproducible identities appropriate to their class.

For Git repositories, this requires an exact commit SHA for inspected code.

### `reference_coverage_ready`

PASS only when required source classes were attempted or a documented reason explains why a source class is not applicable or unavailable.

This gate evaluates acquisition completeness against the plan; it does not claim that the entire literature has been exhausted.

### `reference_novelty_handoff_ready`

PASS only when closest prior work, collisions, borrowed ideas, source-code analogues, unresolved gaps, and limitations are explicit enough for the novelty assessment to proceed.

## 11. Failure modes

At minimum, a future implementation should represent:

- `reference_query_under_specified`
- `source_provider_unavailable`
- `canonical_identity_unresolved`
- `repository_commit_unresolved`
- `paper_code_link_ambiguous`
- `reference_duplicate_conflict`
- `reference_access_blocked`
- `reference_coverage_insufficient`
- `novelty_collision_found`
- `post_outcome_reference_boundary_violation`

`novelty_collision_found` is not an infrastructure failure. It is a valid scientific finding that may force revision of the hypothesis or claim before study lock.

## 12. Agent-role implications

Reference Acquisition is intentionally compatible with future node-level agent assignment.

Potential roles include:

- `paper_scout`
- `source_code_scout`
- `standards_scout`
- `reference_curator`
- `literature_reviewer`

Low-cost/free/local agents may perform retrieval-oriented scout roles, while a stronger harness agent may perform synthesis or adversarial novelty review. The governance contract applies regardless of which agent executes each role.

This document does not implement agent assignment.

## 13. Security and execution boundary

Reference Acquisition is read-oriented by default.

Finding a repository does not authorize cloning arbitrary code into an execution environment, installing its dependencies, or running scripts. Any transition from reference inspection to code execution must pass through the relevant GWF implementation/security boundary.

Credentials used by external indexes or GitHub integrations must remain outside public/static surfaces and follow the existing secret-resolution boundary.

## 14. Acceptance criteria for future implementation

A future v0.8.6 implementation is not complete until it can demonstrate at least:

1. the same research question produces an auditable search plan;
2. paper references preserve stable identity/version where available;
3. retained GitHub references preserve exact commit SHA and relevant paths;
4. rejected and unavailable references remain observable rather than disappearing;
5. paper↔code relationships are explicit rather than inferred from URL proximity;
6. references map to research claims/mechanisms with explicit relation types;
7. pre-study and post-outcome acquisition cannot be silently conflated;
8. novelty assessment consumes the governed reference artifacts;
9. no retrieved reference can silently mutate a frozen study;
10. the complete acquisition chain is reconstructable from evidence and lineage.

## 15. Deferred decisions

The following are intentionally left for implementation design after this specification passes QA:

- exact phase numbering;
- database schema;
- search-provider adapters;
- ranking algorithm;
- query expansion strategy;
- PDF/full-text storage policy;
- repository snapshot/storage policy;
- licensing automation;
- concurrency/parallel scout execution;
- UI representation.

These are deferred implementation choices and do not authorize any code changes.
