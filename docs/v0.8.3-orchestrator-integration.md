# GWF v0.8.3 — Orchestrator Integration & Live Agent Operations

## Baseline

v0.8.3 is based on verified v0.8.2 main commit:

`28a194a133768611dd8e3d6aabbe03c6cbadb9ca`

GitHub `main` remains the source of truth.

## Audit findings

The v0.8.2 agent protocol was persistent and testable, but it was not the mandatory execution path of `ResearchOrchestrator`. Research phases could execute directly while protocol stages were exercised separately through API/tests.

Additional gaps confirmed during the audit:

- research workunits declared `executor_role` but not a formal `skill_ref`;
- skill revisions were not resolved/pinned automatically by the orchestrator;
- handoffs existed but the next phase did not verify a persisted previous-handoff link/hash during preflight;
- phase-stage events were persisted but there was no live backend transport;
- project recovery mode lacked a domain/project/phase resolution hierarchy;
- project governance guarded workunit/run/enqueue/proposal mutation, but orchestration start itself did not call `require_mutable()`;
- GitHub Pages remained static/localStorage UAT and therefore was not a real backend E2E path.

## Locked scope

v0.8.3 implements:

1. **Protocol-driven orchestration**
   - each real research phase resolves a pinned skill;
   - LOAD → PREFLIGHT → PLAN occurs before runtime execution;
   - failures persist a ProblemRecord before retry/replan;
   - successful execution must pass checklist/QA before handoff;
   - handoff must exist before protocol completion.

2. **Domain skill contract**
   - research workunits declare `skill_ref`;
   - domain skill definitions include version, markdown, tool requirements, and QA contract;
   - runtime materializes immutable skill revisions and pins exact revision/hash;
   - execution does not resolve a filesystem `SKILL.md` path.

3. **Verified handoff chain**
   - each executable phase persists its previous phase execution, handoff id, and handoff hash;
   - previous handoff payload hash is recomputed before preflight can pass.

4. **Live operational events**
   - protocol stage events are merged into Process Inspector timelines;
   - backend exposes an SSE stream with event ids and `Last-Event-ID` resume support;
   - no hidden model chain-of-thought is stored or exposed.

5. **Recovery configuration hierarchy**
   - domain default;
   - project default;
   - phase override;
   - domain/phase minimum is monotonic: `HUMAN_APPROVE` cannot be weakened to `AUTO` by a convenience setting.

6. **Archive enforcement**
   - a new orchestration cannot start while the project is `ARCHIVING` or `ARCHIVED`.

7. **Retry durability**
   - runtime retry ordinal is persisted in orchestration state;
   - AUTO recovery persists the new ordinal before the next attempt;
   - a human-approved retry resumes with the next logical attempt even when a new physical WorkUnit is created;
   - exhausted retry is returned as `PAUSE: RETRY_EXHAUSTED`, never allowed to fall through as success.

## Explicit non-goals / claims not made

- No PostgreSQL RLS claim.
- No built-in OIDC/JWKS cryptographic verification claim beyond the existing verifier boundary.
- No arbitrary external exactly-once claim.
- No claim that GitHub Pages/localStorage is an authoritative backend.
- No claim that the current static Pages deployment is backend E2E UAT.
- No tenant-custom skill marketplace in this increment; v0.8.3 pins domain-owned executable skills.
- No hidden chain-of-thought exposure.

## Validation contract

The v0.8.3 gate wraps the complete v0.8.2 gate and additionally requires:

- dedicated v0.8.3 tests on SQLite;
- dedicated v0.8.3 QA on SQLite;
- the same tests on live PostgreSQL;
- the same QA on live PostgreSQL;
- ResearchOrchestrator regression tests on both backends;
- Python compileall;
- v0.8.2 regression PASS, which transitively covers the prior v0.8.1, v0.8, v0.7, v0.6 and v0.5.1 gates.

GitHub Pages is intentionally not redeployed by the v0.8.3 workflow because no static UI files are changed in this increment.
